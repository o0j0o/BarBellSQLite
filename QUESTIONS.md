## 1. Batch format (job number + ProductNo) - RESOLVED, CORRECTED 2026-09-09

**Corrected: batch = job number + ProductNo (`Product.ProdNum`, e.g. `'47388'`), NOT
item number (`Product.Name4`, `'233458'`).** Originally implemented (and confirmed) using
the item number - `'122984233458'` - but the user explicitly corrected this: "the Batch
number is the job number and the product number not the itemNumber." Now:
`'12298447388'` for job 122984 / P/N 47388. `build_batch_number()` in
[`src/batch.py`](src/batch.py) is unchanged (still just concatenates two strings) - what
changed is which value `assemble_label_rows()` passes in.

## 2. Is "item number" the same thing as "customer part number"? - RESOLVED 2026-09-09

**Resolved: they're two different fields, kept separately.** The user clarified that
"ProductNo"/"P/N" specifically means `Product.ProdNum` (the internal Label Traxx
number), which is what feeds the batch (see #1). `Product.Name4` (`'233458'`) is the
separate "item number" field, kept on every label row for its own sake but no longer
tied to the batch. Both are now distinct fields on `LabelRow`/the CSV
(`item_number`/`ItemNumber` and `product_no`/`ProductNo`).

## 4. Where does the GTIN come from? - RESOLVED (2026-09-09, item 3)

Confirmed from the project documents: **JWN owns and provides the GTIN per SKU - CLC must
never create or register one.** It's one of the six required fields on every label (AI
02).

**Resolved: `Product.BC_Start`** ("Barcode Start" in Label Traxx's own UI) is the field -
confirmed by the user. `Product.BC_Symbol`/`BC_HRStart` (checked earlier) decode to a
different number, so those are CLC's own product barcode, not this. `get_product_info()`
in `src/labels.py` reads it through the existing read-only connection wrapper and
validates it via `src/gtin.py::normalize_gtin()`.

**No manual override anymore.** The earlier "enter a GTIN for this run" escape hatch
(built 2026-09-09, before this field was known) is gone - since BC_Start is now the
authoritative source, a missing/invalid value is a **blocking, non-dismissible error**
(see item 12) rather than something to work around in BarBell. This also means item 1's
bold-digit styling (which specifically targeted the "GTIN entered for this run:" line)
no longer has anything to render - see item 12 for the full explanation.

Real BC_Start values pulled from the live database are messy exactly as expected free
text: some use GS1 grouping spaces (`'0 51096 18492 1'` - a genuinely valid UPC-A),
others are truncated/garbage (`'0 12061'` -> 6 digits after despacing, not a valid GTIN
length). `normalize_gtin()` strips whitespace throughout (not just the ends) so the
grouped ones parse correctly, while still catching the genuinely bad ones.

## 5. SSCC generation - BUILT

Confirmed from the project documents: **SSCC is generated by CLC, one unique number per
pallet, never reused - not sourced from Label Traxx at all.** The CLC briefing itself
flags this as the top risk area because CLC runs three plants (Barbados, LCJ,
Dominicana) that could otherwise collide on the same number, and recommends a central
automated generator over per-plant ranges or a spreadsheet.

**Decided: just this plant for now**, not the central multi-plant authority the briefing
recommends long-term.

**Built and initialized (2026-09-09)**: `src/sscc.py` using CLC's real GS1 Company
Prefix (`08600157112`, from the certificate the user supplied - Account 30391419). The
production state file (`sscc_state.json`) is initialized with `last_serial: 9`, so
**serials 0-9 are reserved for samples/testing** (build them directly with `build_sscc()`
- they'll never be issued by `SSCCGenerator.next_sscc()`) and the first real pallet gets
serial 10 (`008600157112000104`).

**Known gap, deferred on purpose**: no cross-process locking on the state file - fine
for one process on one plant, not safe for concurrent processes or multiple plants. See
[docs/gs1_label_requirements.md](docs/gs1_label_requirements.md#sscc-the-missing-piece).

## 11. Scannable barcode images - BUILT (2026-09-09)

You asked whether an actual scannable barcode image could be generated for both the
GS1-128 contents string and the SSCC, so it can be tested on screen before printing -
built as a **"Preview Barcode"** button in `barbell_gui.py` (GUI only - "on screen" is a
GUI concept; the CLI still only prints the text AI strings).

- Uses `python-barcode`'s `Gs1_128` class (a tested Code 128 implementation, not
  hand-rolled) - `src/barcode_render.py::render_barcode_image()`.
- **Important technical detail, easy to get wrong**: the on-screen `(AI)data(AI)data`
  text is for display only - the actual barcode encodes AI digits directly with a
  control character (FNC1, not a printable one) as a separator, required by GS1 rules
  wherever a variable-length field is followed by more data. AI (37) quantity is
  variable-length and not the last field here, so it needs an FNC1 separator before AI
  (10) batch begins; AI (02)/(11) are fixed-length (no separator needed); AI (10) is
  last (no trailing separator needed either). Built in
  `src/gs1.py::build_contents_barcode_data()`/`build_sscc_barcode_data()`.
- **Verified independently, not just by eye**: `tests/test_barcode_image.py` decodes
  the rendered images with `zxing-cpp` - a completely different library from the
  encoder - and asserts the result matches exactly, including against the real example
  you pasted. This is real round-trip proof the encoding is correct, not just that it
  "looks like" a barcode.
- `zxing-cpp`/`numpy` are test-only dependencies (not needed to run the app) - noted as
  such in `requirements.txt`.
